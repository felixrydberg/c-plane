# Storage Service Implementation

This document describes the regional S3-compatible data plane. For the product model, see [Storage](../storage.md).

Both bucket modes share these properties:

- A tenant bucket is a project-level logical resource. Internal platform
  services may own platform-level logical buckets through service credentials.
- Every logical bucket maps to one dedicated real bucket at its regional provider.
- Object bytes remain in the region's configured S3-compatible provider.
- The provider, its bucket names, and its credentials are never exposed to users.
- An object becomes visible atomically. Partial and incomplete uploads are never visible through `GET`, `HEAD`, or `LIST`.

## Proxy buckets

Proxy buckets are the initial implementation. The Storage API is a stateless authenticated proxy and does not maintain its own object namespace or metadata database.

```text
S3 client
    |
    v
Storage API (s3s)
    |-- Control plane: token, bucket, provider, and SSE-C key resolution
    `-- Regional S3 provider: dedicated bucket, object keys, and object bytes
```

For each request, the Storage API:

1. Verifies the platform-issued S3 credential.
2. Resolves the logical bucket and its read/write grant through the control plane.
3. Rewrites the logical name to the dedicated provider bucket name `cp-{bucket_uuid}`.
4. Passes through a complete customer SSE-C triplet or fills the platform bucket key.
5. Streams the request to the provider through `aws-sdk-s3`.
6. Rewrites provider bucket names in responses back to the logical name.

Object keys are forwarded unchanged. Provider S3 owns object metadata, listings, multipart state, versions, checksums, atomic replacement, and durability. `ListBuckets` is built from the authenticated bucket grants rather than the provider's account-wide bucket list.

The proxy supports object reads, writes, heads, deletes, listings, copies, and multipart operations. Logical bucket creation and deletion remain control-plane operations. Copies are limited to buckets using the same provider identity.

### Platform service credentials

Platform services may use the same S3 endpoint for platform-owned buckets that
do not belong to a project. These credentials form a separate tier from tenant
storage access tokens:

- Postgres stores the service name, access-key ID, provider assignment, and
  logical/physical bucket names in the platform service's storage record. For
  Distribution this is the singleton `registry_storage` row.
- OpenBao stores only the secret access key at
  `platform/s3/service-credentials/{credential_id}`.
- The service receives the access-key pair through installation secret
  injection. Backing-provider credentials and bucket SSE-C keys are never
  delivered to it.
- The control plane resolves the access-key ID to the service credential and
  target bucket. Storage then verifies the normal SigV4 signature.

On a cache miss, one `UNION ALL` query resolves either a tenant access token or
the Distribution row and fails closed if both match. Credential resolution
then returns a storage target, so object handlers do not branch on the service
name. Tenant and platform-service requests use the same bucket rewrite,
provider proxy, encryption, and authorization path.

### Future provider mirroring

Provider mirroring is not part of the initial implementation. If required, add
it to generic logical-bucket storage rather than to Distribution:

1. Keep one provider as the authoritative primary.
2. Acknowledge a mutation after it succeeds on the primary.
3. Enqueue durable asynchronous copy or deletion work for configured mirrors.
4. Read from the primary; make failover an explicit control-plane operation.
5. Use the logical bucket's existing SSE-C key for every replica while
   streaming through Storage.

This keeps provider availability independent and makes the capability usable
by both tenant buckets and platform-owned buckets.

## Branching buckets

Branching buckets are a possible future expansion. They keep one dedicated provider bucket per logical bucket and add a C-Plane namespace layer mapping `(project_branch, logical_key)` to immutable provider objects. A branch can then share a snapshot root and copy only changed namespace paths and objects, with O(1) branch creation even for millions of keys.

### Components

The regional Storage deployment has two container roles:

1. **Storage Database** stores bucket-branch roots, immutable namespace nodes, blob metadata, upload sessions, reference counts, and durable release jobs. It is backed by FoundationDB.
2. **Storage API** is the stateless S3-compatible gateway. It authenticates requests, resolves their organization/project/branch, updates the namespace, and streams object data to or from the backing provider.

The existing control-plane Postgres database continues to own user-facing bucket configuration, region placement, and project relationships. It does not serve the object request path.

```text
S3 client
    |
    v
Storage API (s3s)
    |-- FoundationDB: namespace, roots, uploads, release queue
    |-- OpenBao: platform SSE-C bucket keys
    `-- Regional S3 provider: immutable object bytes
```

### Rust libraries

- [`s3s`](https://github.com/s3s-project/s3s) implements the inbound S3 HTTP protocol, XML serialization, request validation, virtual-host parsing, streaming bodies, and AWS Signature V4/V2 verification. The Storage API implements `s3s::S3`.
- [`s3s-aws`](https://crates.io/crates/s3s-aws) bridges useful `s3s` and AWS SDK types.
- [`aws-sdk-s3`](https://crates.io/crates/aws-sdk-s3) talks to the configured regional backing provider.
- [`foundationdb`](https://crates.io/crates/foundationdb) is the Rust client for the transactional metadata store.
- [`reqwest`](https://crates.io/crates/reqwest) calls the OpenBao API using the Storage API's workload identity.
- [`sha2`](https://crates.io/crates/sha2) hashes canonical tree-node bytes to produce immutable node IDs.
- [`bytes`](https://crates.io/crates/bytes) encodes versioned tree nodes in a fixed, deterministic binary format.

Do not use `s3s-fs` in production. It is a filesystem-backed sample intended for tests and local development.

Pin `s3s` and `s3s-aws` to exact reviewed releases. Upstream describes the project as experimental, so upgrades require rerunning the compatibility suite before deployment.

`s3s` is a protocol adapter, not a security boundary or storage engine. The service must configure HTTPS, request/body limits, rate limits, backpressure, authentication, authorization, quotas, and log redaction.

### Credential and branch resolution

Users receive platform-issued `access_key_id`, `secret_access_key`, and `endpoint_url` values. Backend provider credentials remain regional secrets.

Implement:

- `s3s::auth::S3Auth` to resolve an access key to its credential secret and authenticated identity.
- `s3s::access::S3Access` to authorize the requested operation against organization, project, bucket, and project branch.

Credentials are branch-scoped. Resolving an access key must produce at least:

```text
organization_id
project_id
project_branch_id
credential_id
permissions
```

The bucket name identifies the global logical bucket; the credential identifies which branch view is used. Public URLs must also identify a branch explicitly and must never infer one from mutable project state.

### Provider bucket provisioning

`CreateBucket` uses the same provisioning workflow whether it originates from the dashboard/control API or the S3 API:

1. Validate project access and reserve the logical bucket name.
2. Insert the logical bucket in `provisioning` state with a stable UUID.
3. Derive an opaque provider name such as `cp-{bucket_uuid}`. Never use the user-visible name as the provider identity.
4. Call the provider's `CreateBucket` API using regional operator credentials.
5. Configure the provider bucket as private, permit SSE-C where the provider requires explicit enablement, configure lifecycle rules, and restrict provider access to that bucket.
6. Create the empty namespace root and initial bucket-branch records in FoundationDB.
7. Mark the logical bucket `ready` and return the S3 response.

Provisioning is idempotent by logical bucket UUID. If provider creation succeeds but metadata initialization fails, retry initialization; if provisioning is abandoned, delete the still-empty provider bucket and mark the logical bucket `failed`.

The dedicated provider bucket is the second tenant boundary. The first is Storage API authorization and namespace resolution. Provider access must also be bucket-scoped where the provider offers bucket policies, access points, scoped tokens, or equivalent controls; using one unrestricted data-plane principal would make the physical separation structural rather than an authorization boundary.

Backing buckets always remain private. A logical `is_public` setting is enforced by the Storage API so public access still resolves an explicit project branch.

#### Deletion

Bucket deletion moves the logical bucket to `deleting`, rejects new mutations, releases all branch roots, waits for queued physical object deletions, calls the provider's `DeleteBucket`, and finally removes its metadata. A bucket is not reported fully deleted while its provider bucket still exists.

### Physical object layout

Branches do not receive separate provider buckets. All branches of one logical bucket share its dedicated provider bucket and store objects under opaque immutable keys:

```text
objects/{blob_id}
```

The user's logical key exists only in the namespace tree. Never overwrite a provider object in place. A logical overwrite uploads a new blob and publishes a new namespace root.

### Namespace: immutable Merkle B+ tree

Each bucket branch stores one `root_hash`. The hash identifies an immutable B+ tree root. Internal nodes contain ordered separator keys and child hashes. Leaf nodes contain ordered logical keys and object metadata.

```text
Internal node
  separators: ["m", "t"]
  children:   [hash_a, hash_b, hash_c]

Leaf node
  entries:
    avatars/alice.png -> blob_id, etag, size, content_type, encryption metadata
    avatars/bob.png   -> blob_id, etag, size, content_type, encryption metadata
```

Tree nodes use a versioned canonical binary encoding. A node ID is `SHA-256(encoded_node)`. The encoding must have fixed field order, explicit lengths, bytewise S3 key ordering, and no unordered maps. Changing the format requires a new encoding version.

Target a node value below FoundationDB's 100 KB value limit. Start with 32-64 KiB nodes and tune using realistic key and metadata sizes.

#### Branch creation

Create a bucket branch by transactionally copying the parent's current `root_hash` into a new root record and incrementing that root node's reference count. No tree node or blob is copied.

When a project branch is created, repeat this constant-size operation for each branch-enabled bucket. Historical project revisions must pin the bucket root hashes that belonged to that revision.

#### Mutation

To add, overwrite, or delete a key:

1. Read the branch root and generation.
2. Walk to the target leaf.
3. Create a replacement leaf.
4. Rebuild and hash only the nodes on the path to the root.
5. In one FoundationDB transaction, insert the new immutable nodes, update reference counts, and compare-and-swap the branch root/generation.
6. Retry from the latest root if another writer won the race.

Tree cost is O(log n). Branch ancestry does not affect lookup or listing cost.

#### Reads and listing

- `GET` and `HEAD` walk from the selected branch root to one leaf, then resolve the immutable provider blob.
- `LIST` walks to the first requested prefix/cursor and iterates leaves in bytewise key order.
- A continuation token contains the snapshot `root_hash`, last logical key, and request parameters, protected by an HMAC. Later pages therefore remain on the same snapshot while writes continue.

### Blob lifecycle and reference counting

Every immutable node has a reference count for incoming root and parent-node edges. Every blob has a reference count for leaf entries.

Counts represent stored graph edges, not the number of branches that can reach an item. Creating a new immutable node increments each outgoing child/blob edge exactly once. Reusing an already-stored node increments only that node's incoming count; it must not increment all of that node's children again.

- Creating a branch increments only the shared root's count.
- Publishing a replacement root increments references introduced by new nodes and releases the old root.
- When a node count reaches zero, enqueue `release_node(node_hash)` in the same FoundationDB transaction.
- Releasing an internal node decrements its children.
- Releasing a leaf decrements its blobs.
- When a blob reaches zero, enqueue `release_blob(blob_id)`.

The release queue is durable, deletion-triggered work rather than a periodic full-tree scan. A worker claims jobs transactionally and records attempts and errors. Release progress must be observable for branch and bucket deletion.

Before deleting provider bytes, `release_blob` transactionally changes the zero-reference blob to `deleting`. A later attempt to reuse identical content must create a new blob while that state is active. Physical deletion is retried until confirmed.

### Upload sessions

Uploads may last for hours. Persist an upload session before returning an upload ID or accepting object data:

```text
upload_id
bucket_id
project_branch_id
logical_key
provider_upload_id
physical_key
status
expected_size
expected_checksum
created_at
expires_at
error
```

Multipart parts are separate records keyed by `(upload_id, part_number)`. Do not store all parts in one FoundationDB value; S3 permits enough parts to exceed a single value's size limit.

States:

```text
initiated -> uploading -> verifying -> committing -> completed
                    \-> aborted | expired | failed
```

Rules:

- The session is created before the Storage API starts the provider multipart upload.
- The client streams parts to the Storage API. The API forwards the stream to the provider with the platform SSE-C headers; it never buffers a complete object.
- Parts are written to an opaque staging/physical key and are never represented in the namespace tree.
- Do not write one metadata transaction per progress byte. Record completed parts and optionally accept throttled progress heartbeats.
- `CompleteMultipartUpload` verifies provider completion, size, checksums, and conditions before publishing the new tree root.
- The blob record, tree mutation, and `completed` upload state are committed atomically in FoundationDB.
- `If-Match` and `If-None-Match` conditions are rechecked against the current root at completion; long uploads never lock a logical key.
- Provider lifecycle rules abort abandoned multipart uploads after the configured TTL. Expired metadata is safe because it is not reachable from a tree root.

### Platform-managed SSE-C keys

Every logical bucket has a random 256-bit platform SSE-C key. Store it at a path such as `storage/sse-c/{bucket_id}` in OpenBao. The Storage API receives read access through workload identity; the control plane, FoundationDB, logs, and clients do not receive the raw key.

For every provider operation that reads or writes a platform-encrypted object, the Storage API loads the bucket key and sends:

```text
x-amz-server-side-encryption-customer-algorithm: AES256
x-amz-server-side-encryption-customer-key: <bucket key>
x-amz-server-side-encryption-customer-key-MD5: <computed MD5>
```

This is provider-side encryption: the Storage API pipes plaintext bytes but does not encrypt, decrypt, or buffer the full object itself. The provider stores ciphertext.

The key is intentionally separate from provider credentials. A leak of provider credentials alone cannot decrypt stored objects, though it can still threaten availability through listing or deletion. This is defense in depth, not protection from a fully privileged Storage API or OpenBao operator.

Do not issue backing-provider presigned URLs for platform-encrypted objects. The URL recipient would need the raw SSE-C key header. Clients may still generate ordinary S3 presigned requests for the Storage API endpoint; the API verifies the request signature and retains the platform key server-side.

### Customer-provided SSE-C request fields

The API supports the following `s3s` input fields for server-side encryption with customer-provided keys:

- `sse_customer_algorithm`
- `sse_customer_key`
- `sse_customer_key_md5`

They correspond to:

```text
x-amz-server-side-encryption-customer-algorithm
x-amz-server-side-encryption-customer-key
x-amz-server-side-encryption-customer-key-MD5
```

Requirements:

- All three fields are required together when SSE-C is used.
- The supported algorithm is `AES256`.
- Validate the MD5 digest before forwarding object data.
- Never persist or log `sse_customer_key`.
- Persist only non-secret encryption metadata needed for later validation and responses, such as algorithm and key MD5.
- A user-provided SSE-C key replaces the platform bucket key for that object. The client must provide the same key on later reads and copies.
- Forward the selected platform or user key to backing-provider `PUT`, multipart, `GET`, `HEAD`, and copy operations. The regional provider must support SSE-C before the capability is advertised.

`s3s` parses these fields but does not implement their storage semantics; the Storage API remains responsible for validation, redaction, forwarding, and correct errors.

### Initial S3 operation surface

Implement these `s3s::S3` methods first:

- Bucket: `create_bucket`, `delete_bucket`, `head_bucket`, `get_bucket_location`, `list_buckets`
- Objects: `get_object`, `head_object`, `put_object`, `delete_object`, `delete_objects`, `copy_object`
- Listing: `list_objects`, `list_objects_v2`
- Multipart: `create_multipart_upload`, `upload_part`, `upload_part_copy`, `list_parts`, `list_multipart_uploads`, `complete_multipart_upload`, `abort_multipart_upload`

Return the S3 `NotImplemented` error for unsupported operations. Do not silently accept configuration that has no effect.

### Consistency and failure rules

- A root update is the linearization point for a completed object mutation.
- Provider bytes must be durable before their blob becomes reachable from a root.
- A successful `CreateBucket` response requires both the provider bucket and empty namespace root to exist.
- A provider upload without a committed tree root is an orphan and can be safely released after its upload/session retention window.
- Immutable nodes may be written more than once because their content hash makes writes idempotent.
- The gateway must never buffer an entire object in memory. Request and response bodies remain streaming.
- A failed release must not restore namespace visibility; it remains queued until physical cleanup succeeds.

### Deployment

- External endpoint: `s3.<region>.platform.dev`.
- Internal endpoint: `s3.internal`.
- Run multiple stateless Storage API replicas behind the regional gateway.
- Keep FoundationDB and backing-provider traffic inside the region.
- Authenticate the Storage API to OpenBao with workload identity and mTLS; restrict it to the bucket-key paths it needs.
- Store provider credentials and HMAC signing keys in the regional secret system.
- Redact authorization headers, platform and customer encryption keys, presigned query strings, and provider credentials from logs and traces.

### Verification

The compatibility suite must exercise the AWS CLI, `aws-sdk-s3`, and boto3 against the gateway. At minimum, cover:

- SigV4 headers and presigned requests
- virtual-host and path-style addressing
- streaming and ranged reads
- conditional writes
- multipart resume, abort, competing completion, and service restart
- stable paginated listing while the branch changes
- O(1) branch creation with millions of keys
- branch isolation and historical root restoration
- SSE-C success, missing fields, wrong MD5, wrong key, and log redaction
- provider credential leakage cannot decrypt platform-encrypted test objects
- reference counts and release retries under concurrent branch deletion and writes

# S3 architecture

## Model

Each tenant logical bucket belongs to one project and maps to one dedicated
physical provider bucket. Internal platform services may instead own a global
logical bucket through a dedicated platform service credential.

```text
logical bucket `assets` -> provider bucket `cp-{bucket_uuid}`
```

The provider bucket name is opaque. Clients see only the logical name. Physical buckets are never shared between logical buckets.

## Request path

```text
S3 client
  -> Storage service
  -> API
  -> Valkey cache
  -> S3-compatible provider
```

The Storage service calls the API for S3 access-token resolution and provider
credentials. It has no process-local secret cache. The API reads OpenBao and
owns the S3 resolution cache. The control plane accesses only provider secrets
while managing S3 providers.

Tenant access tokens and platform service credentials use the same SigV4
verification and resolved storage-target path. Distribution's access-key ID
and provider/bucket assignment live in `registry_storage`; its secret access
key lives in an access-key record at
`cplane/data/platform/s3/access-keys/{access_key_id}` in OpenBao. A cache miss uses that
record to establish the database scope and verify the current credential. Object
handlers do not branch on the service name.

On a normal cache hit, an object read or write does not call OpenBao or Postgres for token resolution:

1. Storage verifies the request signature with the resolved platform S3 secret.
2. Storage checks the token's logical-bucket read/write grant.
3. Storage rewrites the logical bucket name to `cp-{bucket_uuid}`.
4. Storage sends the request to the provider with the selected SSE-C headers.

Object bytes stream between Storage and the provider. OpenBao never receives object data.

## Valkey cache

Valkey stores a complete resolved access-token response: the platform S3
secret, organization/project identity, bucket grants, provider IDs, and
platform SSE-C keys. Provider credentials are read directly from OpenBao when
needed and are not separately cached.

Resolved token responses are versioned by a single cache generation and expire after 24 hours. Updating the generation invalidates every old response without scanning keys. The following operations advance it after their database transaction commits:

- access-token creation, revocation, and permission changes;
- bucket and project deletion;
- region changes or deletion;
- provider update or deletion; and
- organization deletion.

On a cache miss, the API reads OpenBao and Postgres, verifies current active
state and permissions, builds the response, and stores it in Valkey. OpenBao is
therefore a provisioning and cache-miss path, not the normal S3 object request
path.

## Encryption keys

Every logical bucket has one random 256-bit platform SSE-C key. It is created during logical-bucket provisioning and stored in OpenBao at:

```text
cplane/data/storage/sse-c/{bucket_uuid}
```

The same key is used for every platform-encrypted object in that logical bucket. It is not one key per object and it is not shared across an organization. This gives bucket-level encryption isolation: a key for one logical bucket cannot decrypt objects in another. There is no legacy-key fallback; installation and bucket provisioning create the key.

For requests without a complete customer SSE-C triplet, Storage fills the provider's `AES256` SSE-C algorithm, key, and MD5 headers using the platform bucket key. A client may instead provide a complete SSE-C triplet; that object then requires the same client key for later reads.

## Security boundary

This design keeps provider credentials and platform SSE-C keys away from S3 clients. A provider credential alone does not provide the bucket SSE-C key required to read platform-encrypted objects.

Valkey is intentionally an internal-only service: Compose does not publish port `6379` to the host. Its contents are still plaintext to processes that can connect to Valkey, so Docker-network isolation is not sufficient as a production secret boundary. Production must use Valkey authentication/ACLs and restrict access to the API. Treat the Valkey volume, API process memory, and OpenBao credentials as sensitive.

OpenBao remains the durable secret store. Valkey is a shared cache and can be rebuilt from OpenBao after a restart.

## Non-goals

- Storage does not maintain an object metadata database or object namespace layer.
- Storage does not create one encryption key per object.
- Storage does not expose provider bucket names, provider credentials, or platform SSE-C keys to clients.
- Storage does not access Valkey directly.
- Storage does not initially mirror buckets. Future mirroring belongs to the
  generic logical-bucket target and replication queue, not a service-specific
  S3 endpoint.

# S3 architecture

## Model

Each logical bucket belongs to one project and maps to one dedicated physical provider bucket:

```text
logical bucket `assets` -> provider bucket `cp-{bucket_uuid}`
```

The provider bucket name is opaque. Clients see only the logical name. Physical buckets are never shared between logical buckets.

## Request path

```text
S3 client
  -> Storage service
  -> Control plane
  -> Valkey cache
  -> S3-compatible provider
```

The Storage service calls the Control Plane for S3 access-token resolution and provider credentials. It has no process-local secret cache. The Control Plane should be the only service that reads or writes Valkey (Let UI have its own instance of Valkey).

On a normal cache hit, an object read or write does not call OpenBao or Postgres for token resolution:

1. Storage verifies the request signature with the resolved platform S3 secret.
2. Storage checks the token's logical-bucket read/write grant.
3. Storage rewrites the logical bucket name to `cp-{bucket_uuid}`.
4. Storage sends the request to the provider with the selected SSE-C headers.

Object bytes stream between Storage and the provider. OpenBao never receives object data.

## Valkey cache

Valkey stores two kinds of plaintext secret material:

- Provider credentials, keyed by provider ID.
- A complete resolved access-token response: the platform S3 secret, organization/project identity, bucket grants, provider IDs, and platform SSE-C keys.

Resolved token responses are versioned by a single cache generation and expire after 24 hours. Updating the generation invalidates every old response without scanning keys. The following operations advance it after their database transaction commits:

- access-token creation, revocation, and permission changes;
- bucket and project deletion;
- region changes or deletion;
- provider update or deletion; and
- organization deletion.

On a cache miss, the Control Plane reads OpenBao and Postgres, builds the response, and stores it in Valkey. OpenBao is therefore a provisioning and cache-miss path, not the normal S3 object request path.

## Encryption keys

Every logical bucket has one random 256-bit platform SSE-C key. It is created during logical-bucket provisioning and stored in OpenBao at:

```text
cplane/data/storage/sse-c/{bucket_uuid}
```

The same key is used for every platform-encrypted object in that logical bucket. It is not one key per object and it is not shared across an organization. This gives bucket-level encryption isolation: a key for one logical bucket cannot decrypt objects in another. Resolution retains a lazy fallback only for buckets created before key provisioning was added.

For requests without a complete customer SSE-C triplet, Storage fills the provider's `AES256` SSE-C algorithm, key, and MD5 headers using the platform bucket key. A client may instead provide a complete SSE-C triplet; that object then requires the same client key for later reads.

## Security boundary

This design keeps provider credentials and platform SSE-C keys away from S3 clients. A provider credential alone does not provide the bucket SSE-C key required to read platform-encrypted objects.

Valkey is intentionally an internal-only service: Compose does not publish port `6379` to the host. Its contents are still plaintext to processes that can connect to Valkey, so Docker-network isolation is not sufficient as a production secret boundary. Production must use Valkey authentication/ACLs and restrict access to the Control Plane. Treat the Valkey volume, Control Plane process memory, and OpenBao credentials as sensitive.

OpenBao remains the durable secret store. Valkey is a shared cache and can be rebuilt from OpenBao after a restart.

## Non-goals

- Storage does not maintain an object metadata database or object namespace layer.
- Storage does not create one encryption key per object.
- Storage does not expose provider bucket names, provider credentials, or platform SSE-C keys to clients.
- Storage does not access Valkey directly.

# S3 architecture

## Model

A foundation `bucket` is the physical authorization target. A `credential`
receives read/write access to it through `bucket_grant`:

```text
credential -> bucket_grant -> foundation bucket -> S3 provider

Tenant storage and managed Registry records reference their logical region separately;
the foundation bucket stores the resolved backing S3 provider directly.
```

`bucket_grant` contains only organization scope, prefix, and permissions. It
does not contain a logical product bucket name and does not depend on
`storage_bucket`.

Logical S3 names are derived during credential resolution:

- Customer Storage: `bucket_grant -> bucket -> storage_bucket`.
- Managed Registry: `bucket_grant -> bucket -> managed_registry`, with the
  fixed logical name `registry`.
- Platform/internal storage: its existing logical-name metadata.

## Request path

```text
S3 client -> Storage -> API resolver -> foundation bucket provider
```

The resolver validates an active credential directly, decrypts its tenant or
platform secret, loads its foundation-bucket grants, derives their logical
names from product metadata, and returns provider routing plus the bucket SSE-C
key. A `storage_access_token` row is not required to validate a credential;
that table remains customer product metadata.

Storage verifies SigV4, checks the resolved logical-bucket permission, rewrites
the logical name to the opaque physical bucket, supplies platform SSE-C headers
when the client did not supply a complete triplet, and streams the request to
the provider. Registry traffic uses this same resolver and proxy path.

## Cache and invalidation

The API stores complete resolved credential responses in Valkey. Storage has
no process-local credential secret cache. Resolution cache entries include the
credential secret, prefix, grants, provider routing, and SSE-C keys; provider
credentials remain separately resolved by the API.

Credential, grant, bucket, region, provider, and organization mutations
invalidate affected resolved data through the existing cache generation and
targeted invalidation paths.

## Security boundary

Provider credentials and platform SSE-C keys are never returned to S3 clients.
Each foundation bucket has its own random 256-bit SSE-C key in OpenBao, so a
provider credential alone cannot decrypt platform-encrypted objects. Valkey,
API memory, OpenBao credentials, and persistent volumes remain sensitive.

Physical bucket IDs are the IDs returned by resolution. Product identifiers
and project metadata stay at the product layer and are not moved into grants.

# S3 Service — Platform Architecture Summary

## 🎯 Goal

Provide a **platform-native S3-compatible storage service** where:

* users interact with a standard S3 API
* authentication and permissions are controlled by your platform
* storage backend is pluggable
* clusters remain disposable
* persistence exists at the **region level**, not cluster level

The platform becomes a **managed S3 gateway**, not a storage provider itself.

This aligns directly with your storage model where object storage is the durability layer .

---

# 1️⃣ Core Design Principle

> The platform exposes S3.
> The platform does NOT expose storage providers.

Users never interact with AWS, R2, Ceph, etc.

```
User
  ↓
Platform S3 Endpoint
  ↓
Storage Adapter Layer
  ↓
Backend Object Storage
```

---

## Separation of Responsibilities

| Layer           | Responsibility          |
| --------------- | ----------------------- |
| Platform API    | auth, limits, isolation |
| S3 Gateway      | protocol compatibility  |
| Storage Adapter | provider translation    |
| Backend Storage | durability              |

---

# 2️⃣ High-Level Request Flow

```
Client (AWS SDK / rclone / app)
        │
        ▼
S3-Compatible Endpoint
(storage.platform.dev)
        │
        ▼
Auth Layer
(validate platform credentials)
        │
        ▼
Workspace Resolution
(RLS + capability checks)
        │
        ▼
Storage Adapter
(provider abstraction)
        │
        ▼
AWS S3 / R2 / Ceph / MinIO
(using platform credentials)
```

Users believe they are using S3 directly.

Providers see only **your platform account**.

---

# 3️⃣ Credential Model

## User Credentials (Platform-Owned)

Users receive:

```
access_key_id
secret_access_key
endpoint_url
```

These belong to **your platform**, not the backend provider.

Stored in:

* workspace-scoped tables
* enforced via data-scoped permissions 

---

## Backend Credentials (Internal Only)

Your platform stores:

```
provider_access_key
provider_secret
region config
bucket mapping
```

These are NEVER exposed externally.

---

## Credential Translation

At request time:

```
User credentials
      ↓ validate
Platform identity resolved
      ↓
Mapped → backend credentials
      ↓
Signed request sent to provider
```

This is **not reselling**, because users never receive provider access.

---

# 4️⃣ Bucket Model

Buckets are logical platform resources.

### Platform Bucket

```
workspace_id
region_id
bucket_name
storage_backend
provider_bucket
prefix
```

Example mapping:

```
User bucket:   media
Provider bucket: platform-prod-eu
Prefix: workspaces/ws_123/media/
```

Benefits:

✅ single provider bucket possible
✅ strong isolation
✅ easier migrations
✅ per-workspace quotas

---

# 5️⃣ Storage Backend Abstraction

Each region defines a storage backend:

```
Region EU-West
   → Cloudflare R2

Region US-East
   → AWS S3

Self-host region
   → Ceph RGW
```

Matches your region abstraction where regions define durability boundaries .

---

## Adapter Interface (Conceptual)

```
trait ObjectStorage {
  put_object()
  get_object()
  delete_object()
  list_objects()
  generate_signed_url()
}
```

Providers become interchangeable.

---

# 6️⃣ Request Execution Modes

## Mode A — Proxy (Default)

Platform forwards requests.

```
Client → Platform → Provider → Platform → Client
```

Pros:

* full auditing
* quota enforcement
* simple security

Best starting point.

---

## Mode B — Signed Redirect (Scale Mode)

Platform returns temporary signed URLs.

```
Client → Platform (auth)
          ↓
   signed URL issued
          ↓
Client → Provider directly
```

Pros:

* massive bandwidth savings
* cloud-scale uploads/downloads

---

# 7️⃣ Integration with Platform Architecture

## Storage Philosophy

From your storage design:

> Clusters are disposable; object storage is durable .

Therefore:

* S3 lives at **region layer**
* clusters never own data
* workloads write directly to S3

---

## Cluster Interaction

Workloads inside clusters use:

```
https://s3.internal.region
```

NOT provider endpoints.

This enables:

* backend migration
* traffic shaping
* internal networking later

---

# 8️⃣ Security Model

### Isolation Layers

1. Workspace identity
2. Bucket ownership
3. Prefix scoping
4. Capability limits
5. Provider credential isolation

Clusters never access tenant storage directly, preserving your control-plane boundaries .

# 9️⃣ Compliance & TOS Position

This architecture is compliant because:

✅ users authenticate to **your service**
✅ provider credentials remain private
✅ you operate as an application layer
✅ storage is infrastructure dependency

You are offering:

> “An S3-compatible storage service backed by object storage.”

NOT:

> “Reselling AWS/R2 accounts.”
